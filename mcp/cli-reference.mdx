## Overview

The Summer Engine CLI (`summer`) installs the engine, configures your AI agent, manages projects, signs you in, runs the MCP server, and runs any Summer operation from the shell (`summer <area> <action>`, see [Operations from the shell](#operations-from-the-shell)). Run any command without a global install using `npx`:

```bash
npx -y summer-engine@latest <command>
```

Or install the `summer` command once and run `summer <command>`: `brew install summerengine/tap/summer` (Homebrew) or `npm install -g summer-engine` (npm, Node 20+).

The fastest way to get started is the one-line setup, which wires up your agent's MCP config, installs the whole skill library, and runs diagnostics in a single step:

```bash
npx -y summer-engine@latest setup claude-code --yes
```

Swap `claude-code` for any id on [Every Supported Agent](/mcp/agents).

## Commands

### summer setup

Configure Summer Engine for an AI agent and run diagnostics in one step. This is the recommended onboarding command. It writes the MCP server config for the agent, installs the whole skill library where that agent reads skills, and prints a doctor report. Every agent and the files it writes: [Every Supported Agent](/mcp/agents).

```bash
summer setup <agent> [--yes] [--cli] [--allow-rules] [--scope user|project] [--force] [--recommended] [--stable-only] [--channel <tag>]
```

| Argument / Option | Description |
|-------------------|-------------|
| `<agent>` | Agent to configure: `claude-code`, `claude-desktop`, `codex`, `cursor`, `windsurf`, `antigravity`, `cline`, `cline-cli`, `kilo-code`, `github-copilot`, `vscode-copilot`, `visual-studio`, `copilot-jetbrains`, `opencode`, `zed`, `kiro`, `goose`, `hermes`, `trae`, `qwen-code`, `kimi-code`, `crush`, `amp`, `factory`, `junie`, `warp`, `rovo-dev`, `qoder`, `grok-build`, `mistral-vibe`, `lm-studio`. Legacy, still accepted: `gemini`, `roo-code`. Aliases such as `claude`, `devin`, `agy`, `copilot`, `droid` resolve too |
| `--yes` | Apply the practical setup steps (including skill install) without prompting |
| `--cli` | CLI only: install the skills and no MCP server. The agent runs `summer` commands in its shell. `--no-mcp` does the same |
| `--allow-rules` | With `--cli`, for Claude Code and Codex: let the agent run read-only `summer` commands, and dry runs of spends, without asking. Prints every rule; writes them only with `--yes`. Run it only when the person asks |
| `--remove-allow-rules` | Remove the rules `--allow-rules` added, and nothing else |
| `--scope <scope>` | Config scope: `user` (default) or `project` |
| `--dry-run` | Show planned changes without writing files |
| `--print` | Print the MCP config snippet instead of writing files |
| `--force` | Rewrite every installed skill and remove copies older Summer versions wrote elsewhere |
| `--recommended` | Install only the recommended skill subset instead of the whole library |
| `--stable-only` | Skip skills marked preview |
| `--channel <tag>` | npm dist-tag the MCP entry runs (`latest` by default; `next` while a release soaks) |
| `--json` | Print the setup result as JSON |

**Examples:**

```bash
npx -y summer-engine@latest setup claude-code --yes
npx -y summer-engine@latest setup cursor --yes --scope project
npx -y summer-engine@latest setup zed --print             # See the config without writing
npx -y summer-engine@latest setup goose --yes             # YAML config, written in place
npx -y summer-engine@latest setup codex --cli --yes       # Skills only, no MCP server
```

### summer doctor

Diagnose your setup end-to-end: Node version, CLI version, skills freshness, login, engine install, the local engine API, project memory, and MCP server boot.

```bash
summer doctor [--json]
```

| Option | Description |
|--------|-------------|
| `--json` | Print diagnostics as JSON |

Run this first whenever something is not working. Each check reports either OK or a clear next step, such as "engine not running" or "not signed in".

### summer install

Download and install Summer Engine to your system.

```bash
summer install [--path <dir>]
```

| Option | Description |
|--------|-------------|
| `--path <dir>` | Custom install directory (macOS default is `/Applications/Summer.app`) |

**Platforms:** macOS and Windows. Linux users download manually from [summerengine.com](https://www.summerengine.com/download).

**What it does:** Fetches the latest release, downloads the installer, and installs the app. On macOS it mounts the DMG and copies `Summer.app` to Applications. On Windows it runs the installer. After install, run `summer login`, then `summer run`.

---

### summer login

Sign in to your Summer Engine account via browser OAuth.

```bash
summer login [--force] [--store] [--no-store]
```

| Option | Description |
|--------|-------------|
| `--force` | Re-authenticate even if already logged in |
| `--store` | Repeat only the store sign-in |
| `--no-store` | Only the Summer account sign-in; skip the store sign-in |

**What it does:** Opens your browser once: you sign in to your Summer account with Google, GitHub, or email, then approve the store, publishing and Grow tools. The CLI saves `~/.summer/auth-token` and `~/.summer/oauth-token`. One sign-in covers every cloud operation. The MCP server uses a separate local token (`~/.summer/api-token`) for engine communication.

---

### summer logout

Clear your saved auth tokens.

```bash
summer logout
```

Removes `~/.summer/auth-token` and cached user info. Does not affect the engine's local API token. Run `summer login` again to re-authenticate.

---

### summer status

Check engine status, API connection, and auth state.

```bash
summer status
```

Reports whether you are logged in (and with which email), whether the engine is running (and which project and scene are open), and the local API port and token presence.

### summer run

Launch Summer Engine, optionally opening a project.

```bash
summer run [path]
```

| Argument | Description |
|----------|-------------|
| `path` | Path to a project directory (must contain `project.godot`). Optional. |

**What it does:** Finds the Summer Engine binary, spawns it with `--editor`, and optionally passes `--path <projectPath>`. Waits for the local API to respond (up to 20 seconds). If the engine is already running, it reports the current state and exits.

**Examples:**

```bash
summer run                    # Launch engine (no project)
summer run my-game            # Launch and open my-game/
summer run ./projects/racer   # Launch and open a relative path
```

---

### summer open

Open a project in Summer Engine.

```bash
summer open <path>
```

| Argument | Description |
|----------|-------------|
| `path` | Path to a project directory (must contain `project.godot`) |

**What it does:** Resolves the path and checks for `project.godot`. If the engine is not running, it launches with that project. If the engine is already running, it prints the path and a note: to switch projects, close the current one in the engine first or run `summer run <path>`.

### summer create

Create a new project from a template.

```bash
summer create <template> [name]
```

| Argument | Description |
|----------|-------------|
| `template` | Built-in slug (`empty`, `3d-basic`) or any community template slug |
| `name` | Project directory name (defaults to the template slug) |

**Built-in templates** work offline:

| Template | Description |
|----------|-------------|
| `empty` | Empty 3D project with a root Node3D |
| `3d-basic` | 3D scene with Camera3D, DirectionalLight3D, floor mesh, and sky |

Community templates clone from `github.com/SummerEngine/template-*`. Run `summer list templates` to browse them. Pass `--keep-git` to keep the upstream `.git` directory after cloning (default is to detach so you start fresh).

**Examples:**

```bash
summer create 3d-basic my-game     # Built-in template
summer create empty                # Built-in template
summer list templates              # Browse community templates
```

---

### summer list

List available templates or local projects.

```bash
summer list <what>
```

| Argument | Description |
|----------|-------------|
| `what` | `templates` or `projects` |

- **templates:** Shows the built-in templates plus community templates from `github.com/SummerEngine`.
- **projects:** Scans the current directory for subdirectories containing `project.godot`.

### summer plan

Plan the right Summer CLI/MCP workflow for an AI game-building task. Takes a goal in plain English and prints the recommended skills, MCP tool groups, host-file work, user gates, and next steps. Useful as a planning aid before you ask your agent to build something.

```bash
summer plan <goal...> [--json]
```

| Argument / Option | Description |
|-------------------|-------------|
| `<goal...>` | What you want to build, fix, polish, or create |
| `--mode <mode>` | Optional task mode override |
| `--target <target>` | Optional task target override |
| `--asset-policy <policy>` | Optional asset policy override |
| `--verification <level>` | Optional verification level override |
| `--json` | Print the plan as JSON |

**Example:**

```bash
summer plan make a small arena shooter
```

This is the CLI surface of the same router exposed to agents as the `docs.plan` operation (3.x name `summer_start_game_task`).

### summer memory

Inspect a project's durable memory in its `.summer` directory. Project memory is where agents store the game brief, art and audio bibles, the build plan, and locked facts like voice IDs and world canon.

```bash
summer memory [--project <path>] [--json]
summer memory show <file> [--project <path>]
summer memory path [--project <path>]
```

| Command | Description |
|---------|-------------|
| `summer memory` | Print a summary of `.summer` memory: file counts, canonical files, and locked facts |
| `summer memory show <file>` | Print a specific `.summer` Markdown file (must live inside `.summer`) |
| `summer memory path` | Print the `.summer` directory path for the current project |

| Option | Description |
|--------|-------------|
| `--project <path>` | Project directory to inspect (defaults to the current directory or the running engine's project) |
| `--json` | Print the summary as JSON |

**Example:**

```bash
summer memory
summer memory show .summer/memory/casting/voices.md
```

### summer mcp

Start the MCP server for AI tool integration.

```bash
summer mcp [--profile <profile>] [--toolsets <list>] [--project <path>] [--instance <id>]
```

| Option | Description |
|--------|-------------|
| `--profile <profile>` | `full` (default), `engine` (engine, generation and the store; for clients with a tool limit) or `assets` (generation and the asset library, no engine). Env: `SUMMER_PROFILE` |
| `--toolsets <list>` | Comma-separated toolsets to add. `summer mcp --help` lists them. Env: `SUMMER_TOOLSETS` |
| `--project <path>` | Bind engine tools to the editor running this project |
| `--instance <id>` | Bind engine tools to one exact Summer Engine instance |

**What it does:** Starts the MCP server on stdio. Your IDE or agent invokes this automatically when it loads the MCP config you wrote with `summer setup`, so you rarely run it by hand. Engine tools keep their names (`summer_add_node`, `summer_run_script`, `summer_play`, `summer_screenshot`). Cloud work goes through a short list of direct tools plus `summer_search` (find an operation) and `summer_call` (run it); after `summer login` the server carries every cloud operation. See the [Operations reference](/mcp/operations).

There is also a lower-level `summer mcp setup <agent>` subcommand that writes only the MCP config (no skills, no diagnostics). Prefer the top-level `summer setup <agent>` for onboarding.

### summer skills

Install and manage best-practice guides for AI agents building games. Skills are Markdown files that teach the agent patterns for scene composition, character controllers, asset generation, debugging, and more.

```bash
summer skills list                          # List available skills
summer skills list --by-domain              # Grouped by primary domain
summer skills install <name> --agent <a>    # Install one skill for an agent
summer skills install --recommended --agent <a>   # Install the recommended set
summer skills install --all --agent <a>     # Install every skill
summer skills info <name>                   # Show description and preview
```

| Option | Description |
|--------|-------------|
| `--agent <agent>` | Target agent (any id from `summer setup`, or `summer` for `~/.summer/skills`) so the skill installs where that agent auto-discovers it |
| `--scope <scope>` | `user` (default) or `project` |
| `--stable-only` | With `--all` / `--recommended`, skip skills marked preview |
| `--recommended` | Install the recommended skill set |
| `--all` | Install every available skill |
| `--force` | Overwrite existing skill content on re-install |

Most users never call this directly: `summer setup <agent> --yes` installs the whole library for you. See [Skills](/mcp/skills) for the catalog and where each agent reads skills.

### summer tool

Run any Summer tool from the shell, with the same code the MCP runs.

```bash
summer tool --list                                    # Every tool with a one-line summary
summer tool <name> [--args '<json>']                  # Run one: a slug (add-node) or an MCP name (summer_add_node)
```

Engine tools need Summer Engine running with the project open.

---

### summer config

Read or change the shared `~/.summer` configuration.

```bash
summer config [--json]
summer config get <key>
summer config set <key> <value>
summer config unset <key>
```

---

### summer events

Print recent engine events, or follow them live.

```bash
summer events [--follow] [--kinds <csv>] [--limit <n>] [--json]
```

`--kinds` takes event kinds such as `play.started,script.error`. Output is JSON lines when piped.

---

### summer debug

Write a support-ready Markdown report of what is broken.

```bash
summer debug [issue...] [--play] [-o <path>] [--json]
```

`--play` also launches the game briefly and collects what happened after play.

## Operations from the shell

Every Summer operation runs from the shell, with the same input and the same answer as in the MCP. Every operation and its input: [Operations reference](/mcp/operations).

```bash
summer <area> <action> [--<field> <value> ...] [--input '<json>'] [--dry-run] [--idempotency-key <k>] [--wait] [--json]
```

- **Names are kebab-case.** The operation `assets.generate_image` is `summer assets generate-image`, and its input `aspectRatio` is `--aspect-ratio`.
- **Fields:** `--<field> <value>` for each input field; `--no-<field>` sets it to false; repeat a flag for a list. `--input '<json>'` passes the whole input, or the parts that are objects.
- `--dry-run`: check and describe the call. Nothing changes, nothing is spent.
- `--idempotency-key <k>`: the retry key. Operations that go live or move money require it.
- `--wait`: follow a job or an approval to the end. The approval link prints first.
- `--json`: print the answer envelope only. See [How Summer answers](/api-reference/mcp).
- **Exit code:** `0` for any ok answer (`done`, `running`, `needs_approval`, `dry_run`), `1` for an error.

Cloud operations run after `summer login`. Engine and local operations run on your computer and need Summer Engine open; `--dry-run` checks their input without it.

| Command | What it does |
|---|---|
| `summer whoami` | Who is signed in, the agent app, plan and credits |
| `summer ops search <words...>` | Find operations from the job in plain words (`--area`, `--limit`, `--json`). Works signed out: cloud operations show "(needs sign-in)" |
| `summer ops describe <op>` | One operation with its exact input |

**Examples:**

```bash
summer whoami
summer ops search set a game price
summer ops describe pricing.set_base
summer games list --json
summer assets generate-image --prompt "a knight in a misty forest" --aspect-ratio 16:9 --wait --json
summer store status --game-id <gameId> --json
summer store publish --game-id <gameId> --idempotency-key <k> --input '{"price":{"currency":"USD","amountMinor":499}}' --dry-run
```

`summer tool <slug>` stays: it runs a tool by its slug or 3.x name.

## Environment Variables

| Variable | Description |
|----------|-------------|
| `SUMMER_GATEWAY_URL` | Override the auth/gateway URL (default `https://www.summerengine.com`). Used for local development. |
| `SUMMER_TOKEN` | A Summer account token. It wins over `~/.summer/auth-token`; `summer logout` does not clear it. |
| `SUMMER_PROFILE` | The `summer mcp --profile` default |
| `SUMMER_TOOLSETS` | The `summer mcp --toolsets` default |
| `SUMMER_NO_TELEMETRY` | `1` stops signed-in MCP sessions from reporting each tool call to Summer |

There is no environment variable for the engine port. The CLI reads the port from the
`~/.summer/api-port` file listed below, which the engine writes on startup, and falls back
to `6550` when that file is absent.

## File Locations

| Path | Purpose |
|------|---------|
| `~/.summer/auth-token` | User auth token (from `summer login`) |
| `~/.summer/oauth-token`, `~/.summer/oauth-client` | The store sign-in (from `summer login`); it renews itself |
| `~/.summer/user.json` | Cached user info (id, email, name) |
| `~/.summer/api-token` | Local engine API token (created by the engine on startup) |
| `~/.summer/api-port` | Port override if the default 6550 is occupied |
| `.summer/` | Per-project durable memory (game brief, bibles, locked facts) |
| `~/.agents/skills/` | Shared agentskills.io skills folder, read by Codex, Cursor, Zed, OpenCode, Copilot in VS Code, Devin Desktop and others (`.agents/skills/` in a project) |
| `<skills dir>/.summer-version` | Marker `summer doctor` uses to detect stale skills |
