A big project has more code than the agent can read in one turn. These habits
help the Summer Engine agent find the right files and make changes that fit
your project.

## How the agent finds code

- **Project Intelligence** indexes your project so the agent can search it. See
  [Project Intelligence](/ai-tools/rag-search).
- **@ mentions** point the agent at exact files and folders. See
  [Working with context](/guides/working-with-context).
- **Subagents** explore and do focused work, so the main chat stays short. See
  [How Summer's AI agents build your game](/ai-tools/subagents).
- **Rules** tell the agent your conventions in every chat. See below.

## Get up to speed

Start with broad questions, then narrow down.

```
What does the combat system look like in this project?
Show me how player input flows from @input/ to the player script.
Where is save and load implemented?
What depends on @autoload/event_bus.gd?
```

## Rules for consistency

Write your conventions down once. Summer reads these files at the start of
each chat:

| File | When it applies |
|---|---|
| `AGENTS.md` at the project root | Every chat |
| `.summerrules` at the project root | Every chat |
| `.summer/rules/*.md` (or `.mdc`) | Every chat, or only when the files you work on match its `globs` |

A rule file in `.summer/rules/` can have frontmatter. With `globs` and no
`alwaysApply: true`, the rule applies only when the chat works on matching
files.

```markdown title=".summer/rules/combat.md"
---
globs: "scripts/combat/**"
---

1. Combat entities extend CombatEntity.
2. Damage goes through DamageCalculator.calculate_damage().
3. Status effects go through StatusEffectManager.
4. Combat events are emitted on CombatEventBus.
```

Keep rules short. Summer reads up to 20 KB from each of `AGENTS.md` and
`.summerrules`, and about 24,000 characters of rules in total.

For decisions about your game itself (art style, mechanics), use
[Memory](/ai-tools/memory). For a repeatable way of working, write a
[Skill](/ai-tools/skills).

## Plan big changes first

Ask for a plan before the agent edits anything.

```
I want to add crafting to this RPG. Look at @inventory/, @items/ and @ui/.
Do not change files yet. Write a plan: where the scripts go, how crafting
uses the inventory, which UI we need, and how recipes are stored.
Ask me questions if something is unclear.
```

Then do the plan in steps you can test:

```
Do step 1 only: create the Recipe resource and two example recipes.
```

To approve each edit yourself, set the chat's permission mode to **Manual**.
**Accept edits** runs project edits and still asks before paid tools and
commands.

## Point at working examples

The agent copies patterns well. Name the file to copy.

```
Create a spell ability like @abilities/melee_ability.gd.
Use the targeting from @abilities/ranged_ability.gd and the cooldown
from @systems/cooldown_manager.gd.
```

## Keep systems apart

Tell the agent what a system must not do. This stops changes from spreading.

```
The inventory system only stores items, stacks and splits them, and emits
inventory_changed. It does not update UI, apply item effects or change
player stats.
```

## Keep chats focused

- Start a new chat for each feature or bug.
- When you start a new chat, say in two or three lines what the system is and
  where it lives.
- Narrow the scope: "Only change files in @ui/ for this fix."

## Debug in order

Give the error and the path the data takes.

```
Player stats do not save. Check in order:
1. @player/player_stats.gd: do the stats change?
2. @systems/save_system.gd: are they written to the save data?
3. @data/save_data.gd: is the field there?
```

To isolate a bug, ask for a small test scene that loads only the systems
involved.
